21. Worked high-level designs

Each design follows the same spine and only spends words on what is new. Numbers are assumptions you should recompute in practice.

21.1 Rate limiter

Job. Allow N actions per identity per window. Refuse the rest with 429.

Needs. Correct enough under several application servers. Fast, because it sits on every request. A small burst may be allowed. Different routes have different allowances.

Size. At 8,000 requests per second, the limiter runs 8,000 checks a second. Each check is a cache increment, not a SQL transaction.

Design. A shared cache holds a token bucket per key. The key is userId:route or ip:route. The value is the token count and the last refill timestamp. Refill is computed from elapsed time, so you do not need a timer per key: tokens = min(capacity, tokens + elapsed × rate). Then subtract one if a token remains.

Do the read-modify-write inside one atomic cache script so two servers cannot both spend the last token. Put the limiter in the gateway and also in the service that must protect itself if the gateway is bypassed.

Fails. If the cache is down, decide in advance: fail open (allow traffic) or fail closed (refuse). Login limits fail closed. A homepage may fail open. State the choice.

21.2 Unique id service

Job. Mint ids that are unique, roughly time-ordered, and available when any one application server is up.

Design. Snowflake-style 64-bit numbers. Reserve 1 bit, 41 bits of milliseconds since a custom epoch (about 69 years), 10 bits of machine id (1024 machines), 12 bits of sequence (4096 ids per machine per millisecond). A machine that would exceed 4096 in the same millisecond waits until the next millisecond. Machine ids come from a small coordinator or from the orchestration system, and they are unique while the process lives.

Clock going backward is the bug. If the new timestamp is older than the last one used, wait until the clock catches the last timestamp, or refuse to mint and alarm. Do not reuse sequence numbers in the past.

21.3 Chat

Functional. One-to-one and group messages, history, online presence, delivered and read marks, and a push when the person is offline.

Non-functional. Delivery under a second when both are online. History durable. Order stable inside one conversation. A group may have hundreds of members; a broadcast channel is a different product.

Size assumption. 50 million daily senders, 20 messages each, is 1 billion messages a day, about 12,000 writes per second average, perhaps 30,000 at peak. Each message is about 200 bytes of metadata plus text. A year is on the order of tens of terabytes, sharded.

API and connection. WebSocket for send and for live receive. GET /conversations/{id}/messages?before=cursor for history. POST is a fallback when the socket is down.

Data. Conversations, members, and messages keyed by (conversation_id, message_id). Shard by conversation id so one history is one shard and stays ordered. A per-conversation increasing id, or a Snowflake id plus a gap-filling rule, gives order. Inbox pointer: for each user, the list of conversation ids and the latest message id, so the chat list is one read.

Path. Client sends on its socket to Gateway A. Gateway A writes the message to the store, then looks up each member’s gateway in the connection registry and forwards. If a member has no gateway, it writes a push-notification job. The sender receives an ack with the message id. Recipients send delivered and read events, which update small rows and fan out the same way.

Presence is a TTL key in the cache, refreshed by heartbeat. It is allowed to be wrong for seconds.

Hard parts. Gateway fanout for a large group: write once, then push to N gateways, not N database copies of the body. Deduplicate retries with a client message token. Do not let one huge group stall a worker: cap fanout parallelism. Media goes to object storage; the message holds the key.

21.4 Photo feed

Functional. Post a photo and a caption, follow people, open a home feed, like, comment.

Non-functional. Feed open is fast. Posting returns when the photo is safe to acknowledge, not when every follower’s feed is updated. A celebrity can have millions of followers.

Size assumption. 10 million daily posters, one photo each. 100 million daily feed opens. Photos average 2 MB. That is about 20 TB of new images a day before you count replicas and thumbnails. Metadata is the smaller SQL problem. Bytes are the object-storage and CDN problem.

Path, post. Client uploads the file to object storage, directly with a signed upload URL so the bytes do not pass through your application server. The server writes the photo row, enqueues thumbnail and abuse-scan jobs, and enqueues fanout. The client sees the post as soon as the row exists. Followers see it when fanout or read-merge reaches them.

Path, feed. Hybrid fanout from chapter 14. Cache the first page of each user’s prebuilt feed. Likes can be counted in a cache and flushed, with the exact count allowed to lag, or stored as rows if you must list who liked.

Data. Users, follows (follower_id, followee_id), photos (id, owner, object key, time), feed entries (user_id, photo_id, time). Shard follows and feed entries by the reader’s user id, because the hot read is “my feed.” Shard photos by photo id. The celebrity is excluded from write-fanout and merged at read.

Hard parts. Upload resumes for bad networks: object storage multipart upload. Thumbnail so the feed never downloads full-size images. Authorization on every photo URL: private photos use signed URLs that expire, public photos sit on the CDN.

21.5 Notifications

Job. Tell a user that something happened, on the channels they allow: in-app, mobile push, email, maybe SMS.

Path. A service emits an event: “photo 9 was liked by user 3.” A notification service looks up subscribers and preferences, writes an in-app row, and enqueues one job per external channel. Channel workers talk to providers. A preference of “no email” drops that job. A rate cap stops one viral photo from emailing you fifty times in a minute: collapse them into “Priya and 49 others liked your photo.”

Data. Notification rows for the in-app inbox, keyed by user id. Delivery log with provider ids so retries are idempotent. Preferences per user per event type per channel.

Hard parts. Provider outages go to retries and a dead-letter queue. Idempotency key is the event id plus channel plus user. Quiet hours are a product rule in the worker, not a special database.

21.6 Video streaming

Functional. Upload a video, play it, pause, and switch quality as the network changes.

Non-functional. Playback starts quickly. Upload may take minutes. Many viewers watch a few popular videos.

Upload. Multipart upload to object storage. A row is created in a “processing” state. A queue runs transcoding into several bitrates and splits each into short segments (a few seconds). A manifest file lists the segments. When the ladder of qualities is ready, the row becomes “playable.”

Playback. The client fetches the manifest from your API or from the CDN, then fetches segments from the CDN. The client picks a bitrate that fits the current bandwidth. Your origin sees a segment only on a CDN miss.

Data. Video metadata in SQL. Segments in object storage. View counts via a queue, like TinyLink clicks. Recommendations are an offline or nearline job writing “related ids” back to a store the play page can read quickly.

Hard parts. Popular videos are a CDN problem, not an application-server problem. Live video is the same shape with smaller segment duration and a manifest that grows. Protect upload with quotas so one client cannot fill the bucket.

21.7 File sync

Job. A folder on a laptop stays in agreement with a folder in the cloud and with other devices.

Design. Split files into chunks of a few megabytes. Hash each chunk. Upload only chunks the server does not have, which also deduplicates identical chunks across users if you are careful about privacy and encryption. Metadata is a tree: folders, file names, and an ordered list of chunk hashes. Each save creates a new version rather than overwriting the only copy, so you can undo.

Sync. The client sends a local change list. The server applies it when it does not conflict. Two devices editing the same file while offline create two versions; the product shows a conflict and keeps both. A cursor per device says “I have seen everything up to change 500.”

Hard parts. Chunk hashes must be strong. Encryption: if the server stores only ciphertext, deduplication across users gets much harder, and you should say which goal wins. Sharing a folder is an authorization list on the metadata, plus a way to revoke.

21.8 Search and autocomplete

Search. Documents live in the source database. An indexer tails the change stream and updates an inverted index. Queries hit a search service that fans out to index shards and merges the top results. Cache frequent queries. Ranking features that change slowly can be stored beside each post; features that change every second, such as “liked one second ago,” are applied only to the top few candidates.

Autocomplete. On each keystroke, read a precomputed top-10 for that prefix from cache. Build those lists from aggregated query logs in a job that runs every few minutes. Filter with a blocklist before the list is published. Personal history is merged from a small per-user cache. The latency budget is tight, often under 50 ms, so this path is cache only. A miss returns an empty list or a shorter prefix’s list, and a job fills the missing prefix later.

21.9 Web crawler

Job. Given some seed URLs, fetch pages, extract links, and repeat, without melting any host and without fetching the same URL forever.

Pieces. A URL frontier (a queue, ideally prioritized and partitioned by host). Fetchers. A parser that extracts links and content. A dedup store. A politeness rule: at most one fetch at a time to a host, with a delay. A Bloom filter in front of the dedup store answers “definitely new” quickly; “maybe seen” checks the store.

Hard parts. The frontier is the product. If you use one queue, a huge site crowds out the rest. Partition by host so politeness and fairness are natural. Respect a site’s crawl rules as a product and legal requirement. Store content in object storage and metadata in a table. Retries need a cap because some URLs never succeed.

21.10 Payments

Job. Take a payment for an order exactly once, know the state afterward, and be able to reconcile with the outside provider.

Design. Your service is not the bank. It talks to a payment provider. The order service creates a payment row in state pending with an idempotency key. It calls the provider with that same key. The provider’s webhook, and a background poll, move the row to succeeded or failed. The webhook and the poll can both arrive; the state machine ignores a repeated success. Money movement is recorded as a ledger: append-only entries of debit and credit, not a single balance that you edit in place. The balance is the sum of entries, or a cached sum you can rebuild.

State machine. pending → succeeded, pending → failed, succeeded → refund_pending → refunded. There is no path from failed to succeeded without a new payment attempt and a new idempotency key.

Hard parts. The provider said yes and your process died before you stored it. The poll or the webhook heals this; both are required because webhooks get lost. Never trust the browser’s “payment worked” as the source of truth. Reconciliation compares your ledger to the provider’s report every day and alarms on mismatches.

21.11 Metrics and monitoring

Job. Ingest numeric samples from many services and answer “what was the error rate over the last five minutes?”

Design. Each service emits samples: name, tags, timestamp, value. A collector aggregates locally (sum, count, histogram buckets) so you do not ship every request as its own row. Aggregates flow to a time-series store, partitioned by metric name and time bucket. Queries read pre-aggregated buckets, not raw events. Alert rules run on the same store on a schedule.

Hard parts. Cardinality. A tag whose value is a user id creates millions of series and melts the store. Tags are low-cardinality labels such as service, route, and status. Histograms beat averages, because an average hides a slow tail. Keep raw logs somewhere else; this system stores numbers.

21.12 News ticker / pub-sub

Job. Publishers emit topics. Subscribers receive the topics they joined.

Design. A topic is a log partition set. Publishers append. Subscriber groups track offsets. For live UI subscribers, a gateway holds the socket and reads the log. Retention keeps history for replay. This is the queue chapter specialized to many independent readers. The new point is fanout to readers: a message stays in the log once, and each group has its own offset. You do not copy the payload per reader inside the log.

What these designs share

  • A source of truth, and derived copies (cache, search, feed, CDN) you can rebuild.
  • A short path for the user and a queue for the slow part.
  • An idempotency key wherever a retry could double-charge, double-post, or double-send.
  • A shard key taken from the hot lookup.
  • A stated freshness rule: strong for money and unique names, lagged for counts, presence, and search.

22. The LLD method and object rules

Low-level design starts after the city map exists, or beside it when the problem is mostly rules inside one program. The reader of your LLD should be able to write the code.

Steps

  1. Use cases, written as actor plus action.
  2. Nouns become classes. Messages become small data objects.
  3. Relationships: who calls whom, and who holds a list of whom.
  4. Methods on the service that match the use cases. Walk the hottest use case line by line.
  5. Interfaces at the edges: database, cache, clock, random, payment provider. Your rules stay testable without those neighbors.
  6. The table, the unique keys, and the update that is safe under two writers.
  7. Edges: empty input, duplicates, expiry, crashes, and two actions at once.

Objects

A class is a blueprint. An object is one built instance. A field is data the object holds. A method is an action it can do.

Encapsulation. Fields stay private. Callers use methods. The class can change how it stores data without changing every caller.

Abstraction. Callers see a small promise, such as findByCode, and do not see SQL.

Inheritance. A class is a special kind of another class and reuses its code. Use it when the sentence “is a kind of” will stay true forever. A Bus is a kind of Vehicle.

Polymorphism. A caller holds the general type and gets the specific behavior. A list of Vehicle calls spotsNeeded(), and a bus returns 5 while a motorcycle returns 1.

Composition. A class holds other objects and asks them to help. LinkService holds a Codec. Prefer composition as the default way to reuse behavior. Inheritance is for a true “is a kind of” relationship.

An interface is a plug shape with no stored data: a list of methods. An abstract class is a partial blueprint: some methods implemented, some left open, and it may hold fields. Use an interface when many unrelated classes should fit the same plug. Use an abstract class when the shared code is real and the children are the same family.

SOLID

  • Single responsibility. One reason to change. A codec that also opens SQL connections changes when the encoding changes and when the database changes. Split them.
  • Open for extension, closed for modification. A new fee rule is a new class, not an edit inside leave().
  • Liskov substitution. Anything passed in as the interface must keep the promise. If findByCode says “return null when missing,” every implementation does that. A surprise exception breaks callers.
  • Interface segregation. Small plugs. A class that only inserts links does not implement a 30-method administration interface.
  • Dependency inversion. The service depends on the plug, not on the SQL class. The SQL class is passed in at construction. Tests pass a fake.

A readable shape for request code

Controller  - HTTP, status codes, auth checks at the door
Service     - rules and decisions
Repository  - load and save
Entity      - the fact, with small helpers that never touch the network
Clock, IdSource, Cache, Queue - plugs

Validation of shape (missing field, too long) can live at the controller. Validation of meaning (this seat is taken, this code is expired) lives in the service, because it is a rule even when the caller is not HTTP.

UML you actually draw

Class diagram. A box per class. A line with a diamond means “owns a collection of.” An arrow means “calls” or “holds.” A dashed arrow to an interface means “fits this plug.” You do not need every field on the diagram. Put the fields that explain the design.

Sequence diagram. Lifelines across the top, time downward, arrows for calls. Draw one for the hot use case and one for the failure you are proud of handling.

State diagram. Bubbles for states, arrows for events. Draw one whenever a thing has a lifecycle: payment, seat hold, elevator, vending machine. If you cannot name the states, you do not understand the rules yet.

24. Concurrency inside one process

Two threads of the same program can run your method at the same time. The bugs are real even when you have one server.

A race is two threads reading a value, both adding one, and both writing back. One update disappears. A view counter implemented as read-modify-write in application memory has this bug. Fixes: an atomic increment, a database expression set count = count + 1, or a lock around the whole read-modify-write.

A lock (mutex) lets one thread into a block at a time. Keep the block short. Do not call the network while holding a lock that other requests need.

A deadlock is two threads each holding a lock the other wants. Prevent it by acquiring locks in a global order: always lock the smaller id first. If you already hold locks and need a third, you probably want a redesign.

A thread pool is a fixed set of workers pulling tasks. Unbounded thread creation under load exhausts memory. Queue in front of the pool, and when the queue is full, reject.

Immutable objects never change after construction. They need no lock to be shared for reading. A new version is a new object.

In an LLD interview or a design doc, say which data is touched by two threads and which of these tools you use. “The seat map is guarded by one lock per show, and the lock is held only around the in-memory check and the database conditional update” is a complete answer. A conditional update, update seats set owner = ? where id = ? and owner is null, lets the database be the lock. Check the affected-row count. Zero means someone else took it.

State the cost you care about. “Get and put are both O(1)” is the whole reason an LRU cache is a hash map plus a doubly linked list, and not a list you scan.

LRU cache, because it is both a structure and a design

Goal: get and put in constant time, and when capacity is exceeded, drop the least recently used key.

A hash map gives the node for a key. A doubly linked list gives order: the head is most recently used, the tail is least. get moves the node to the head. put of a new key adds at the head and, if over capacity, deletes the tail from the list and the map. put of an existing key updates the value and moves the node to the head. The map and the list always contain the same keys. One lock around both updates keeps them agreeing, or the structure is used by a single thread inside a shard.

26. Testing a design

A design you cannot test is unfinished. Write tests against the service, with fakes for the plugs.

  • Repository fake is a hash map. It enforces the same unique keys the database would, so a test can prove the 409 path.
  • Clock fake returns a time you set, so expiry tests do not sleep.
  • Queue fake records published notes.
  • Cache fake is a map that can be cleared to simulate a flush.

Cases worth writing before you trust the service:

  • The happy path of each use case.
  • Invalid input.
  • Not found, and found-but-expired.
  • The same request token twice.
  • Two creates with the same custom code.
  • A cache hit, a cache miss, and a cache that throws. The service should still read the database when the cache throws, if that was your HLD choice.
  • A conditional update that affects zero rows.

Concurrency tests start two threads on the last seat or the last token and assert that exactly one wins. Flaky tests that sleep and hope are weak. A deterministic interleaving, or a database constraint you can observe, is strong.
