7. Caching

A cache holds a copy so the next reader skips a slower store. You add one when the same read happens over and over, and a slightly older copy is acceptable for a defined time.

Where it sits

  • Browser and CDN. Close to the user. Good for public files and responses that are the same for everyone.
  • Application memory. Fastest, and private to one server. A second server has a cold copy. Useful for tiny, process-local data.
  • Shared cache (a system such as Redis or Memcached). Every application server sees the same shelf. This is the usual box in an HLD diagram.

How writes meet the shelf

StyleWhat happensYou accept
Cache-asideThe application reads the cache. On a miss it reads the database and puts the value in the cache. Writes update the database and delete or replace the cache key.A brief window where the cache is empty or old. This is the default for TinyLink.
Read-throughThe application asks only the cache. On a miss the cache library loads from the database.The same window, with the load hidden inside the cache client.
Write-throughA write updates the cache and the database before success returns.Slower writes. The cache matches the database after each successful write.
Write-backA write updates the cache and returns. A later flush writes the database.Very fast writes, and lost data if the cache dies before the flush.
Write-aroundA write goes to the database, and the cache key is deleted. The next read fills the cache.The next read is a miss. You avoid filling the cache with data nobody rereads.

Deleting a key on write (invalidation) is safer than updating it in place when several kinds of writes exist. A stale key with a TTL (time to live) is a backstop: even if you forget to delete, the copy dies on schedule. TTL alone makes the maximum staleness equal to the TTL. Invalidation plus TTL is the usual pair.

Eviction

The shelf has a size. When it is full, something leaves.

  • LRU, least recently used. Drop what nobody has touched in the longest time. A strong default.
  • LFU, least frequently used. Drop what is used least often. Better when a few keys are steady favorites, and worse right after a key becomes popular, because it has a low count so far.
  • FIFO. Drop the oldest resident, regardless of use.

Stampede

A popular key expires. A thousand requests miss at once and all query the database. That is a thundering herd, also called a cache stampede. Defenses:

  • Single flight. The first miss loads the database. The others wait for that one load and share the result.
  • Lock on the key with a short timeout, so only one loader runs.
  • Early refresh. Before the TTL hits zero, one request refreshes the value while others still receive the old one.
  • Serve a slightly stale value while a refresh runs. The reader is told, by your own rule, how old is still allowed.

What to cache, and what to leave

Cache the hot read that is expensive and reusable: TinyLink’s code to long URL, a rendered feed page, a product page. Skip data that is unique per request and never reused. Skip data whose staleness would be a serious bug, such as a one-time password, unless the TTL is the feature. Remember that a cache is not the source of truth. You must be able to rebuild it.

A famous key that everyone wants is a hot key. One cache process can saturate on it. Defenses: replicate that key to several cache nodes and spread reads, or keep an extra copy in application memory for a second or two.

8. Names, doors, and distance

DNS

People type names. Machines use IP addresses. DNS answers “what address is tiny.link?” The answer can be cached at the laptop, at the company resolver, and at the DNS provider. A short DNS TTL lets you move traffic quickly. A long TTL makes the name survive a DNS outage and makes moves slow. The address you publish is often the load balancer, not a single application server.

Load balancers

A layer 4 balancer forwards TCP connections. It is fast and unaware of HTTP. A layer 7 balancer understands HTTP, so it can route /images to one pool and /api to another, and it can retry an idempotent GET against a different server.

Spreading policies: round robin, fewest active connections, or a hash of the client so the same client prefers the same server. Prefer-the-same-server is sticky sessions. Stickiness is a crutch for a server that kept session state in memory. Stateless servers do not need it. Health checks remove a dead server from the pool. The balancer itself must be redundant: two of them, with one address that can move.

CDN

A CDN caches bytes at the edge, near the user. The origin is your real closet. The first user in a city misses and pulls from the origin. Neighbors hit the edge. You control freshness with cache headers and TTLs. A cache key is whatever makes two responses different: the URL, and sometimes a header such as language. If you forget to include a distinguishing header, two users can receive each other’s personalized page. Personalized HTML usually stays uncached. Images, video segments, and public scripts cache well.

To purge, you delete by key or you change the URL (a new file name or query version). Changing the URL is the reliable kind of purge because old edges simply stop being asked.

9. Copies, consistency, and CAP

Replication

One notebook is a single point of failure and a single disk. Replication keeps copies.

  • Synchronous. The leader waits until a follower has the write, then tells the client success. A crash loses less. The write is as slow as the follower.
  • Asynchronous. The leader tells the client success, then the follower catches up. Writes stay fast. If the leader dies before the follower catches up, those last writes can vanish. The gap is replication lag.
  • Semi-synchronous. The leader waits for one follower, and other followers catch up later.

Reads can go to followers to spread load. A follower may be a second behind, so a user who just wrote can read their old value. Read-your-writes is the fix for that feeling: after a user writes, that user’s next reads go to the leader for a short time, or the read waits until the follower has passed that write’s position.

Failover promotes a follower. Automatic failover needs a rule that avoids two leaders. Two leaders accepting writes is a split brain. The usual rule is a majority vote: a leader exists only if a majority of replicas agree it is the leader. A minority side stops accepting writes.

Quorums

With N copies, a write waits for W copies to acknowledge, and a read asks R copies. If R + W > N, the read set and the write set overlap, so the read sees at least one copy that has the latest write. A common choice is N = 3, R = 2, W = 2. Raising W favors fresher data and slower writes. Lowering R favors fast reads. This arithmetic is the heart of quorum systems. Leader-based databases get a similar result by sending the read to the leader.

CAP, then PACELC

A partition is a cut in the network: some machines cannot reach others. While the cut lasts, a system chooses between two behaviors. Consistency here means every successful read sees the latest successful write. Availability means every request receives a non-error answer. During a partition you emphasize one of them.

  • A CP path refuses or waits when it cannot be sure. A bank transfer and a seat sale lean this way.
  • An AP path answers with the best local copy and repairs later. A view counter and a presence dot lean this way.

PACELC adds the quiet hours. If there is a partition (P), you choose availability or consistency (A or C). Else (E), even when the network is fine, you choose latency or consistency (L or C). Waiting for two distant replicas is a consistency choice you pay for on every write, even on a healthy day.

TinyLink’s redirect path answers from cache and from whatever database copy it is allowed to read. Click counts are allowed to lag. A custom-code insert demands the unique index on the leader, because two people must not both believe they own priya.

A ladder of “how fresh”

  • Strong / linearizable. There is a single order of operations. A read sees the latest completed write.
  • Read-your-writes. You see your own updates. Someone else might lag.
  • Monotonic reads. You never go backward in time. Once you have seen version 5, you do not later see version 4.
  • Eventual. Copies converge after updates stop. Before that, readers can disagree.

Name the rung the product needs. “We need strong consistency” for a whole product is rarely true. Payments need a high rung. Feeds work on a lower rung.

10. Sharding

Sharding splits rows across machines so each machine holds a fraction. You shard when one machine’s disk, memory, or write rate is no longer enough. Replication copies the same rows for safety and read spread. Sharding divides rows. You usually do both: each shard has its own replicas.

How a row picks a home

RuleHow it worksWatch for
RangeIds 1–1,000,000 on shard A, the next million on shard BSimple, and the newest range takes all the inserts
Hashhash(key) mod NEven spread. Changing N moves almost every key
Consistent hashKeys and servers sit on a ring. A key walks clockwise to the next serverAdding a server moves only the keys on the neighboring arc
DirectoryA small lookup table says where the key livesFlexible, and the directory itself must be fast and up

Consistent hashing in a little more detail. Picture a circle of positions. Each cache server is placed at several positions (virtual nodes), so one physical server owns many short arcs. A key is hashed onto the circle and stored on the next server clockwise. When a server leaves, its keys move to the next server on the ring. When a server joins, it takes the arc that now points at it. Virtual nodes keep one physical machine from owning a huge arc by luck. This is how shared caches and some databases place keys.

The shard key is the whole design

You can look up by the shard key with one hop. Any other lookup is a scatter: ask every shard, or maintain a second index. TinyLink shards by numeric id, and the code decodes back to the id, so the hot path stays one hop. If the hot path were “all links created this hour,” a hash shard would force a scatter, and you would want a different key or a second store.

A hot shard receives far more than its share. A celebrity’s messages, if you shard messages by user id and everyone writes on that user’s shard, melt one machine. Fixes: split that user’s data further, add a cache, or choose a key with more spread, such as conversation id.

Resharding moves rows to a new home. Do it as a copy, then a catch-up of new writes, then a short switch. Dual-write during the move, and check that both sides match before you trust the new home.

Cross-shard actions, such as a like from a user on shard A on a photo on shard B, do not get a single database transaction. You design them as two local writes plus a repair job, or you route them through a queue.

11. Queues and delivery promises

A queue lets the request path stay short. The server writes “please do this” onto a durable tray and answers the user. Workers pull notes and do the slow job: resize a photo, send mail, add a click, charge a card.

Promises

PromiseMeaningYour job
At most onceThe note is delivered zero or one time. A crash can lose itOnly for work you can afford to skip
At least onceThe note is retried until a worker acknowledges it. A crash after the work and before the ack delivers it againMake the worker idempotent
Effectively onceThe combination of a durable tray and an idempotent worker produces one effectStore the unique id of the note beside the effect, in the same transaction when you can

Most real systems give at least once. Design every consumer as if the same note will arrive twice. TinyLink’s click worker should add clicks in a way that a repeated note does not double-count, or you accept approximate counts and use at-least-once on purpose because a view counter may be approximate. Say which one you chose.

Ordering

A single queue with one worker preserves order. Several workers finish out of order. A log system such as Kafka restores order inside a partition: all messages with the same key, such as a conversation id, stick to one partition and stay ordered there. Different keys run in parallel. Order is per key, not global.

Parts of a log-shaped queue

  • Topic. A named stream, such as clicks.
  • Partition. An ordered shard of that stream.
  • Offset. A position in a partition. The consumer records how far it got.
  • Consumer group. A team of workers that split the partitions. Each partition is read by one member of the group at a time.
  • Retention. The log keeps messages for a time or a size, whether or not they were read. New consumers can replay history. A classic task queue deletes on ack and does not replay a week later.

The outbox

A common bug: the database commits “order placed,” then the process crashes before it publishes “order placed” to the queue. The order exists and the mail never sends. The outbox writes the business row and an outbox row in the same database transaction. A publisher reads the outbox and publishes. If it crashes, it publishes again. Consumers are idempotent. The business change and the intent to publish commit together.

Dead letters and poison

A poison message makes every worker crash. After a few tries, move it to a dead-letter queue and alert a human. Retrying forever stops the line behind it. Retries should wait longer each time (backoff) and should add a little randomness (jitter) so a thousand workers do not retry on the same millisecond.

Backpressure means the producer slows down when the tray is deep. A queue that grows without limit hides a sick consumer until the disk fills. Cap the depth, or slow the producer, and alarm on age: “the oldest click has been waiting 2 minutes.”

12. Transactions, local and distributed

A transaction is a bundle of reads and writes that succeed or fail as one. Transferring money is two balance updates. Doing only one is a bug. Databases give transactions four properties, abbreviated ACID.

  • Atomicity. All of the bundle commits, or none of it does.
  • Consistency. The bundle moves the database from one valid state to another. Constraints and your rules hold.
  • Isolation. Concurrent bundles do not see each other’s half-finished work in the ways the isolation level forbids.
  • Durability. After commit, the result survives a crash. The database writes a log to disk before it says yes.

Isolation levels

LevelWhat a transaction is protected from
Read uncommittedAlmost nothing. You can see another transaction’s uncommitted write (a dirty read)
Read committedDirty reads. Each statement sees only committed data. Two statements in one transaction can still see different values of the same row
Repeatable readA row you read stays stable for the rest of the transaction. A range can still gain new rows (a phantom) in some databases
SerializableThe result matches some one-by-one order of the transactions

Higher isolation costs more locking or more retries. Use the lowest level that keeps the product correct. Seat booking and balances need a high level or an explicit lock. A view counter needs neither.

Two transactions can deadlock: each holds a lock the other wants. The database aborts one. Your code retries the aborted one. Prevent the common case by locking rows in a consistent order, such as always locking the lower account id first.

Across services

A single SQL transaction stops at one database. Two services with two databases need a different plan.

Two-phase commit uses a coordinator. Phase one: every participant prepares and promises it can commit. Phase two: the coordinator tells them all to commit. If the coordinator dies between the phases, participants wait, holding locks. That blocking is why teams avoid two-phase commit across microservices, even though databases use related ideas internally.

A saga is a sequence of local transactions. Each step has a compensating action that undoes it if a later step fails. Place order, reserve stock, take payment. If payment fails, release stock and cancel the order. Compensations are forward actions, not time travel: a sent email is compensated by a second email, not by un-sending.

  • Orchestration. One conductor calls the steps in order and runs compensations on failure. Easier to read.
  • Choreography. Each service listens for events and does its step, emitting the next event. Less central coupling, and harder to see the whole story.

Sagas are atomic in spirit and visible in the middle. Other users can see “stock reserved, payment not taken” for a moment. Design those intermediate states as real product states.

13. Real-time connections

Some products need the server to speak first: a new chat message, a live score, a typing hint.

TechniqueHow it worksFit
Short pollingThe client asks “anything new?” on a timerSimple. Wasteful when nothing is new. Fine for a rare check
Long pollingThe client asks, and the server holds the request until something exists or a timeout hits. The client immediately asks againNear-real-time without a special protocol
Server-Sent EventsOne long HTTP response. The server pushes text events down. The client reconnects with “I last saw event 40”One-direction updates: feeds, scores, notifications
WebSocketA connection that stays open and carries messages both waysChat, games, collaborative editing

A stayed-open connection is state. The server that holds Priya’s socket is the only one that can push to her. Keep a connection registry: user id to gateway machine. When a message is born on any machine, it looks up the gateway and forwards. If Priya is offline, write the message to her inbox and send a phone push. Gateways must be many, and the registry must update on connect and disconnect.

Heartbeats find dead connections. Without them, a phone that lost its radio still looks online.

14. Feeds and fanout

A feed is “what should this person see, in order?” Two ways to build it.

Fanout on write. When Priya posts, the system writes the post id into the prebuilt feed of each follower. Opening the app is a cheap read of your own feed. A user with 10 million followers turns one post into 10 million writes. That user is a celebrity problem.

Fanout on read. The post is stored once. Opening the app looks up who you follow and merges their recent posts. Writes stay cheap. Reads get heavier as you follow more people, and the merge is on the hot path.

Hybrid. Ordinary accounts fan out on write. Celebrities fan out on read: at read time, merge your prebuilt feed with the latest posts from celebrities you follow. This is the usual answer for a large social product.

Ranked feeds add a scorer: recency, affinity, and a few content features. Scoring can run on write (store the score) or on read (rescore the candidates). Candidate generation plus ranking is the shape: pick a few hundred possible posts cheaply, then rank those, then take the top twenty. You do not rank the entire history on every open.

Cursors keep paging stable. Store “the last post id the client rendered” and ask for older ones.

15. More than one city

One data center is one building. A fire, a cut cable, or a bad deploy takes it. Multi-region design is how you keep going.

  • Active-passive. One region serves. Another holds replicas and is ready to take over. Failover takes minutes and may lose the last asynchronous writes. Simpler to reason about.
  • Active-active. Two regions both serve users, usually the users nearest them. Writes in both places can conflict. You need a rule: route a given user’s writes to a home region, or use conflict-free data, or accept last-writer-wins for data where that is harmless.

Home region is the clean rule for accounts and payments: Priya’s rows live in one region, and her writes go there even if she travels. Reads of her own data go there too, or to a local replica that is allowed to be slightly behind. Global public data, such as a viral video file, replicates everywhere through the CDN and object storage.

Latency across an ocean is tens to a couple of hundred milliseconds. A design that does five cross-ocean database calls on one tap will feel broken. Keep the hot path inside one region.

16. Staying up

Failures are ordinary. A design names them.

  • Timeout. Stop waiting. Every remote call has one.
  • Retry. Try again for errors that might vanish: a dropped packet, a 503, a timeout. Do not retry a 400. Retry only idempotent operations, or carry an idempotency key. Use exponential backoff and jitter. Cap the number of tries.
  • Circuit breaker. When a neighbor is failing most calls, stop calling for a short cool-down. A few trial calls check whether it has recovered. This keeps your servers from piling up threads on a sick neighbor.
  • Bulkhead. Separate pools of threads or connections for separate neighbors. A stuck payment call must not consume the threads that serve the homepage.
  • Rate limit. Cap how fast one caller, one IP, or one API key may knock. Algorithms are in chapter 18.
  • Load shedding. When you are overloaded, refuse new work quickly with 503 so the work you did accept can finish. A server that accepts everything and then does it slowly fails everyone.
  • Graceful degradation. If recommendations are down, show the plain feed. The product continues in a smaller form.
  • Idempotency keys. The client sends a unique token. The server stores the token and the response. A retry returns the stored response.

Define a service level objective in plain numbers: “99.9% of opens complete under 100 ms in a month.” An SLI is the measurement (the percentage that met the bar). An SLA is the promise to a customer, often with a consequence. Design the system to the objective, and alarm when the measurement approaches it.

17. Security

Security in system design is a set of boxes and checks, not a coat of paint at the end.

  • TLS. Encrypts data on the network so a stranger on the path cannot read or alter it. Terminate TLS at the load balancer or at the service, and be deliberate about which hop is encrypted inside the data center too.
  • Passwords. Store a slow hash made for passwords (bcrypt, scrypt, or Argon2) with a unique salt. A hash is one-way. Encryption, which can be reversed with a key, is the wrong tool for passwords. The database never needs the original password again; it only needs to check a new hash against the stored hash.
  • Sessions and tokens. After login, the client holds a token. A random session id stored on the server can be revoked by deleting the row. A JWT is a signed bundle of claims (user id, expiry). Anyone can read it. Only the holder of the signing key can mint a valid one. The server checks the signature and the expiry. Revoking a JWT before expiry needs an extra denylist or very short expiry plus a refresh token.
  • OAuth. The user signs in with a specialist (the identity provider). Your app receives a token and never sees the password. Your app still checks authorization itself.
  • Authorization on the server. The client can hide a button. The server still checks “this user owns this link” on every call. Hiding a button is a convenience. The check is the control.
  • Least privilege. The photo service’s database user cannot read the payments tables. A leaked credential then reaches a smaller blast radius.
  • Encryption at rest. Disks and backups are encrypted so a stolen drive is not a stolen database. Keys live in a key service, separate from the data.
  • Input rules. Validate type, length, and allowed characters. Parameterized queries keep user text from becoming SQL. Object keys are generated by you, so a user cannot name a key that overwrites someone else’s file.
  • Rate limits on login and create. They cut password guessing and spam.
  • Secrets. Keys live in a secret store or environment, never in the repository and never in the client application.

18. Seeing a running system

If you cannot see it, you cannot keep the objective.

  • Logs. A line per meaningful event, with a timestamp, a service name, and a request id that every hop copies. Structured fields (user id, code, latency) beat a paragraph of prose when you search later.
  • Metrics. Numbers over time. For a request path, watch rate, errors, and duration. For a machine, watch CPU, memory, disk, and saturation of the pool. For a queue, watch depth and age of the oldest message.
  • Traces. One request’s spans across services: 12 ms in the gateway, 4 ms in the cache, 40 ms in the database. Traces answer “where did the time go?” for a single slow tap.
  • Alerts page a human on symptoms that need action: error rate over the objective, queue age over the budget, disk predicted to fill. A chart you look at in the morning is a dashboard. An alert is a page. Page on few things, or people will sleep through them.

19. One program or many

A monolith is one deployable program with modules inside it. A microservice is a program that owns one business capability and its data, and talks to others over the network.

Start with one program and clear modules while a small team is learning the product. Split a piece out when it has its own scaling need, its own release clock, or its own strict data boundary. TinyLink’s workers can be a module in the same program. A payments system beside a website is a natural split because the security boundary and the consistency needs differ.

Each service owns its tables. Another service asks through the API or listens to events. Reaching into another service’s tables couples you to its private shape and breaks the moment that shape changes.

An API gateway is the front door for external clients: TLS, authentication, rate limits, and routing to services. Internal services may talk directly for speed, still with timeouts.

Service discovery is how a caller finds a healthy instance. A registry tracks “payment service, these three addresses.” The load balancer or a client library consults it.

gRPC is a binary request protocol with a strict contract, often used between services. HTTP JSON is easier for browsers and public APIs. Both are just menus of calls. The design questions in this book do not change when the bytes on the wire change.

20. Tools you will reach for

Unique ids

  • Database sequence. Simple, ordered, and a single allocator. Fine at TinyLink’s 40 writes per second.
  • Blocks. Each server leases a range. Fewer round trips. Holes appear when a server dies. Order is roughly increasing.
  • Snowflake-style 64-bit ids. A timestamp, a machine number, and a per-machine counter. Ids are unique and roughly time-ordered without a central allocator. Clocks must stay close enough that you do not mint the same timestamp-and-counter pair; the usual design uses a sequence within the same millisecond so a clock wobble of one millisecond is handled by waiting or by the counter.
  • Random UUIDs. Unique with extremely high probability and no coordination. They scatter in B-tree indexes, which makes inserts more random. Fine as public tokens. Less fine as the only primary key of a huge high-insert table, unless the database is built for random keys.

Do not use raw auto-increment ids in a public URL if guessing the next id would expose someone else’s data. TinyLink’s codes are public handles on purpose; private resources should use unguessable tokens plus an authorization check.

Hashing

A hash function maps bytes to a fixed-size number. Tiny changes in the input swing the output. Hashes place cache keys, shard keys, and checksums. A cryptographic hash (SHA-256 and its cousins) is what you want when an attacker must not be able to craft a collision. A fast non-cryptographic hash is what you want for a hash table. Password storage uses a slow password hash, which is a different tool from either of those.

Bloom filters

A Bloom filter answers “have I seen this item?” with two results: definitely no, or maybe yes. It is a row of bits. Inserting an item sets k bit positions chosen by k hashes. Asking an item checks those k bits. If any bit is off, the item was never inserted. If all are on, it was probably inserted, or other items happened to set the same bits.

Use one in front of a huge store to skip useless lookups: a crawler asks “have we fetched this URL?” and a definite no avoids the database. A maybe-yes still checks the database. You cannot delete an item from the basic filter, because clearing a bit might belong to another item. Size the bit array from the number of items and the false-yes rate you allow.

Search

A database LIKE '%cat%' scan does not survive a large corpus. A search index inverts the text. The inverted index maps a term to the list of documents that contain it: cat -> doc 4, doc 9, doc 20. A query intersects lists. Ranking then orders the hits using signals such as how rare the term is and where it sits in the document.

The index is derived. The source of truth stays in your database or object store. An indexer consumes a stream of creates and updates and applies them to the index. Search being a few seconds behind the write is normal and should be stated as a product choice. Tokenization, language, and typos are the hard product edges: decide whether “Cats” matches “cat,” and whether a typo returns neighbors.

Autocomplete is a prefix problem. A trie, or a prefix index, maps ca to the ten most common completions. Those top-ten lists can be precomputed from recent query counts so the keystroke path is one cache read. Update the counts asynchronously. Personal suggestions are a second, smaller list merged at read time.

Rate limit algorithms

AlgorithmBehavior
Fixed windowA counter per clock minute. Simple. At the boundary, a caller can send the full allowance twice in two seconds, once at 12:00:59 and once at 12:01:00
Sliding window logStore each timestamp and count those inside the last minute. Accurate. Uses more memory
Sliding window counterKeep the previous window’s count and the current one. Estimate the last minute as a weighted mix. Small memory, small error
Token bucketTokens drip in at a steady rate, up to a bucket size. Each request takes a token. The bucket size is the allowed burst. Empty bucket means refuse
Leaky bucketRequests join a queue that drains at a fixed rate. Bursts are smoothed. Excess spills (is refused) when the queue is full

Store the counters in a shared cache so every application server enforces the same limit. The key is the caller identity plus the route. Return 429 and a hint about when to retry.
