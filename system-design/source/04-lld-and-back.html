27. Worked low-level designs

These are class-level designs. Each one names the states, the plugs, and the race that matters. Pseudocode is a sketch of the rules, not a library you should paste into production without the checks your environment needs.

27.1 TinyLink inside the server

Link
  id, code, longUrl, createdAt, expiresAt, clickCount, requestToken

CreateLinkCommand
  longUrl, customCode or empty, expiresAt or empty, requestToken

LinkService
  create(command) -> Result
  open(code, now) -> Result
  stats(code) -> Result

plugs: LinkRepository, LinkCache, IdSource, Base62Codec, ClickQueue, Clock

create: reject a bad URL in the controller. If requestToken already exists, return the stored link. If customCode is set, insert it and translate a unique-key failure into “taken.” Otherwise id = ids.next(), code = codec.encode(id), insert. Cache after commit.

open: cache get. On miss, repository get, then cache put. Missing means not found. expiresAt before now means gone. Otherwise publish a click and return the long URL. If the cache throws, read the repository anyway.

The repository’s insert is the uniqueness boundary. The service does not check-then-insert without handling the loser of the race. Two custom-code requests can both see “free” and both insert; the database lets one commit.

27.2 Parking lot

Rules. Floors contain rows contain spots. A motorcycle fits a motorcycle spot or larger. A car fits a car spot or a bus-sized run. A bus takes five consecutive free car spots in one row. A ticket records the vehicle, the spots, and the entry time. Leaving frees the spots and charges a fee.

enum SpotSize { MOTORCYCLE, CAR }

Spot
  id, size, free

Vehicle
  plate, spotsNeeded(), preferredSize()
  Motorcycle 1, Car 1, Bus 5

Ticket
  id, plate, spotIds, entryTime

ParkingLot
  park(vehicle, now) -> Ticket or Full
  leave(ticketId, now) -> Fee

FeeCalculator  (strategy)
  fee(entry, exit) -> money

park walks rows and calls row.allocate(vehicle). For a bus, a row scans for five adjacent free car spots and marks them taken together. The walk and the mark happen under a lock per lot, or as a database transaction that re-reads the spots. Then a ticket is saved. If the process crashes after marking spots and before the ticket, a repair job frees spots that have been held with no ticket past a few seconds. Cleaner approach: insert the ticket and the spot updates in one transaction.

leave loads the ticket, marks those spots free, asks the fee strategy, and stores the exit time. Leaving twice returns the same fee and does not free spots twice. That is the idempotent path.

A new fee rule is a new FeeCalculator. The lot does not grow a chain of if-statements.

27.3 Logger

Rules. Callers log a level and a message. The logger writes to one or more appenders: console, file, or a queue. Messages below the configured level are dropped. A change to the level takes effect without restarting callers.

enum Level { DEBUG, INFO, WARN, ERROR }

LogEvent
  time, level, loggerName, message, context map

Appender
  append(event)

Logger
  name, minLevel, appenders
  log(level, message)
    if level < minLevel: return
    event = build
    for appender in appenders: appender.append(event)

LoggerRegistry
  get(name) -> Logger

The registry is the one shared object, injected where you can, looked up where legacy code forces it. Appenders that do I/O belong behind an async buffer with a bounded queue. When the queue is full, drop debug events and count the drops, or block callers; pick one and document it. Formatting is a strategy so JSON and plain text are swappable. Do not let a failing appender throw into the caller’s business path: catch, count, and continue with the other appenders.

27.4 Elevator

Rules. One car for the core design. Floors call up or down. The car has buttons for destination floors. The car serves requests in its current direction, then reverses. This is the LOOK algorithm: go as far as the furthest request in this direction, then turn around. It does not move toward a call it will pass only after reversing, until the current direction is exhausted.

enum Direction { UP, DOWN, IDLE }

Request
  floor, direction or destination

Elevator
  currentFloor, direction, upStops set, downStops set
  call(floor, direction)
  chooseFloor(floor)
  step()  // move one floor or go idle

Scheduler
  // for several cars: pick the car whose extra distance is smallest
  assign(call)

step is the heartbeat. If there is a stop at the current floor in this direction, open doors and clear that stop. Else if stops remain ahead, move one floor. Else if stops exist the other way, flip direction. Else go idle. Internal destination buttons and hall calls both become stops. A hall call upward is a stop only when the car is traveling up or is idle and chooses up.

Several cars: the scheduler assigns a new hall call to the car that can reach it with the least added travel, given that car’s current direction. Once assigned, the call lives on that car. State pattern fits if you prefer classes Idle, MovingUp, MovingDown, DoorsOpen. The step description above is the same machine written as data.

27.5 Movie tickets

Rules. A show has a screen and a start time and a set of seats. A user holds seats for a few minutes while paying, then confirms. Another user cannot take held or sold seats. After the hold expires, the seats return.

Seat
  id, showId, label

Booking
  id, showId, seatIds, userId, state, holdExpiresAt
  states: HELD, CONFIRMED, CANCELLED, EXPIRED

BookingService
  hold(showId, seatIds, userId, now) -> Booking
  confirm(bookingId, paymentToken, now)
  expireHolds(now)

The race is two people holding the last seat. Do not check availability in memory and then insert. Update rows: update seats set hold_id = ? where show_id = ? and seat_id in (...) and hold_id is null and sold = false. If the number of updated rows is smaller than the number requested, roll the transaction back and return “unavailable.” Confirming sets sold = true only if this booking still holds them and payment succeeds. Payment uses the payments design: idempotency key equals booking id.

expireHolds is a worker. It clears holds whose expiry has passed and whose state is still HELD. Confirm and expire can race; the conditional update lets only one win. If payment succeeds and expiry wins first, the payment saga compensates with a refund. Shorten that window by expiring only holds older than the limit and by confirming inside a transaction that rechecks the hold.

27.6 Splitwise

Rules. Users share expenses in a group. Each expense has a payer and a list of shares that sum to the total. The product shows who owes whom. Settling records a payment that reduces debt.

Expense
  id, groupId, payerId, amount, time
Share
  expenseId, userId, amount
Settlement
  fromUser, toUser, amount, time

Ledger
  // derived: for each pair, net balance
  balances(groupId) -> list of (from, to, amount)
  addExpense(expense, shares)
  settle(from, to, amount)

Store expenses and shares as the source of truth, append-only. A balance is the sum of shares minus what has been settled. You may cache balances and rebuild them. Simplify debts for display with a greedy pass: people with positive net and people with negative net, match the smaller amount, repeat. Say that the simplification is a display of the same nets, not a deletion of history. Shares must sum to the expense. Reject the expense otherwise. Edits are new adjusting entries, or a reversal plus a new expense, so history stays explainable.

27.7 ATM

Rules. Read a card, check a PIN, show accounts, dispense cash, or take a deposit. The bank is an external service. The ATM can be cancelled at each step. Cash inventory is local and must not go negative.

states: Idle, CardInserted, Authenticated, Dispensing, OutOfService

Atm
  state
  insertCard(card)
  enterPin(pin)      // calls Bank.authenticate
  withdraw(account, amount)
  cancel()

CashDrawer
  notes: map of denomination -> count
  canDispense(amount)
  plan(amount) -> notes or Cannot
  commit(plan)

Bank (plug)
  authenticate(card, pin)
  debit(account, amount, idempotencyKey)

withdraw: plan the notes locally without dispensing. Call bank.debit with an idempotency key. On success, commit the notes out of the drawer and open the slot. On failure, dispense nothing. If the debit succeeded and the machine loses power before the slot opens, a journal (a local append-only log) records “debited, not dispensed.” On restart the ATM finishes the dispense or reverses the debit. The journal is the heart of the design. PIN tries: after three failures, keep the session dead and notify the bank. Never store the PIN.

27.8 Vending machine

States: Idle, CollectingMoney, Dispensing, ReturningChange. Inventory maps item code to price and count. Inserting money adds to a balance. Selecting an item checks count and balance. Dispensing decrements count. Change is a coin-planning problem like the ATM drawer. Cancel from CollectingMoney returns the balance. A jam in Dispensing goes to an error state that refunds and does not decrement, or decrements only after the sensor says the item dropped. The sensor is the source of truth for “the user received it.”

27.9 Library

Books have copies. Members borrow a copy. Each loan has a due date. A copy is available, on loan, or lost. borrow updates the copy from available to on loan inside a conditional update, then writes a loan row in the same transaction. returnBook closes the loan, computes a fine strategy from how late it is, and marks the copy available. Reservations: a queue per book. When a copy returns, the next reservation is notified and holds the copy for a limited time. Fine rules are a strategy. Membership limits (five books) are a check inside borrow.

27.10 File system

Composite pattern. Entry has a name and a parent. File is a leaf with size and bytes or a pointer to bytes. Directory holds children in a map by name. add, remove, and find(path) live on the directory. Paths split on / and walk from the root. A name collision is an error. Deleting a directory deletes children, or refuses if non-empty; pick one and stick to it. Permissions are an optional check object asked before read and write. This design is in-memory. Persisting it is the file-sync HLD: the tree is metadata, the bytes are chunks.

27.11 Snake

A board is a grid. The snake is a deque of cells, head at one end. Each tick, compute the next head from the direction. If the next cell is a wall or a body cell, the game is over. If it is food, push the head and do not pop the tail, and place new food on a free cell. Otherwise push the head and pop the tail. Direction changes queue at most one turn per tick so a quick double tap cannot reverse into the neck. Food placement uses a set of occupied cells for an O(1) membership test. The game object exposes turn(direction) and tick(). Rendering is a separate observer.

27.12 Chess, the shape

A board is 8 by 8 squares holding a piece or empty. Each piece class implements legalMoves(board, from). A move is from, to, and an optional promotion. The game checks: the piece belongs to the side to move, the destination is in legalMoves, and the move does not leave your king in check. Check is “any opposing legal move attacks the king’s square,” with a careful rule to avoid infinite recursion: the attack test uses raw moves, not the full “does this leave me in check” filter. Special moves are data: castling requires empty squares, unmoved king and rook, and no check along the way. En passant and promotion are explicit branches. History is a list of moves so you can undo. The design is the piece interface plus the check filter. You do not need a class per rule buried in one giant method.

27.13 LRU cache class

Node
  key, value, prev, next

LruCache
  capacity, map, head, tail
  get(key)
    missing -> return empty
    else move node to head, return value
  put(key, value)
    if key exists: update value, move to head
    else: insert at head, map it
          if size > capacity: remove tail from list and map

Head and tail can be sentinel nodes so the empty-list cases disappear. One mutex wraps get and put if the cache is shared. Eviction policy as a strategy is the extension: LFU replaces the list with frequency buckets. The service that uses the cache depends on a Cache interface, not on this class.

27.14 In-memory rate limiter

TokenBucket
  capacity, refillPerSecond, tokens, lastRefillNanos

  tryTake(now)
    refill(now)
    if tokens >= 1: tokens -= 1; return true
    return false

Limiter
  buckets: map of key -> TokenBucket
  allow(key, now)

Refill computes elapsed time and adds tokens, capped at capacity, then sets lastRefillNanos = now. The map and the bucket update share a lock per key, or one lock if traffic is modest. In the HLD, this same math runs as an atomic script in a shared cache. The LLD is the math and the state. A clock plug makes tests move time without sleeping.

27.15 Pub-sub inside one process

Bus
  subscribers: map of topic -> list of handlers
  subscribe(topic, handler)
  publish(topic, event)
    for handler in copy of list: handler(event)

Iterate a copy so a handler can unsubscribe without disturbing the loop. Decide whether handlers run on the publisher’s thread or on a pool. If they run on the publisher’s thread, a slow handler blocks the publisher. If they run on a pool, order is weaker and errors stay off the publisher. Document that choice. Across processes, replace the bus with the queue from the HLD. The interface publish(topic, event) can stay.

28. Checklists, script, and a study plan

The ten-line script

  1. Users can do these actions. I am leaving these other actions out of this version.
  2. The hot path is this action. Reads and writes compare like this. Data lives for this long. This data may lag. This data must not.
  3. Assumptions: these arrivals, these bytes. Result: this many writes per second, this many reads, this much disk. The pressure is on this box.
  4. The menu of calls, including the error codes that matter.
  5. The tables or documents, the primary key, and the index the hot path uses.
  6. The boxes: client, load balancer, stateless servers, source of truth, and any cache, queue, closet, or CDN.
  7. The path the user waits on, in order. Then the work that happens after the answer.
  8. The first thing that breaks, and the single addition that removes it.
  9. Inside the main program: controller, service, repository, and the plugs. The hot method, line by line.
  10. Edges: retry, expiry, two writers, a dead dependency, and the state machine if the thing has a lifecycle.

HLD checklist

  • Functional list and an out-of-scope list
  • Non-functional list: latency, availability, durability, privacy, and allowed staleness
  • QPS, storage, and bandwidth, each with its assumption
  • API, idempotency, pagination, and errors
  • Source of truth, keys, and indexes
  • Derived copies: cache, search, feed, CDN, and how each is rebuilt
  • Shard key chosen from the hot lookup
  • Replication and what a failover can lose
  • User path versus queue path
  • Timeouts, retries, and what is idempotent
  • The rate limit and whether a dead limiter fails open or closed
  • Authn and authz on the server
  • The metric that proves the objective, and the alert
  • The failure of the database leader, the cache, and one application server

LLD checklist

  • Use cases
  • Entities, value objects, and message objects
  • Service methods matching the use cases
  • Interfaces for storage, clock, ids, and external providers
  • State diagram where a lifecycle exists
  • Sequence of the hot use case
  • Unique keys and conditional updates for races
  • Idempotent retries
  • Strategy or state objects where rules will grow
  • Tests listed: happy, invalid, duplicate, race, dependency down

A study order

  1. Chapters 1–6, then explain TinyLink aloud with the script and no notes.
  2. Chapters 7–12. Redo TinyLink and add a cache failure, a shard, and a queue promise.
  3. Design a rate limiter and a unique-id service on paper.
  4. Design chat. Then the photo feed. Then payments. These three cover fanout, storage of bytes, and money.
  5. Chapters 22–26. Implement the LRU cache and the token bucket in real code, with tests.
  6. Parking lot, movie tickets, and ATM. Draw the state diagram before the classes.
  7. One new product a day from the list below, 40 minutes HLD, 20 minutes LLD of the hottest service. Then compare with this book.

Practice products: URL shortener, paste bin, rate limiter, id service, chat, photo feed, video, notifications, search autocomplete, crawler, file sync, payments, metrics, ride matching, hotel booking, collaborative document, leaderboard, news feed ranking, coupon service, inventory checkout.

For each one, the win condition is the same: another person can implement the hot path and can say what happens when the database leader dies.

Mistakes that ruin an otherwise fine design

  • Boxes with no numbers. You cannot know whether one database is enough.
  • A cache with no rule for staleness and no way to rebuild it.
  • A queue consumer that is not idempotent, paired with at-least-once delivery.
  • A shard key that does not match the lookup users actually do.
  • Check-then-act for a unique name or a last seat, with no constraint and no conditional update.
  • Auto-increment ids in a public URL for private data, with no authorization check.
  • A payment flow whose only success signal is the browser.
  • Two leaders, or a failover story you have not thought about.
  • A class that calls a provider, formats HTTP, and computes a fee. Split the reasons to change.
  • A design that cannot name the source of truth.

A last page you can recite

Every system is a hot path, a source of truth, and a set of copies you can rebuild. The path the user waits on stays short. Slow work goes to a queue. Retries are safe because the operation is idempotent or carries a token. Unique claims and last seats are decided by a constraint or a conditional update, not by a hopeful check. Freshness is a choice you name: money and ownership sit high, counts and search sit lower. Inside the program, rules live in a service, storage lives behind a plug, and growing rules become new classes. If you can say those sentences about a product, with numbers, you understand its design.

End of the offline guide. System design, HLD and LLD, from zero.
