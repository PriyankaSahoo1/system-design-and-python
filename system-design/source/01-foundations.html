System Design from Zero

High-level design and low-level design. A complete offline guide.

This book teaches both maps of a software system. High-level design (HLD) is the city: machines, roads between them, and what happens when the city is busy or something breaks. Low-level design (LLD) is one building: the classes, the methods, the tables, and the rules inside a program.

You do not need a job, a course, or prior vocabulary. Every term is defined at the moment it is used. Later chapters reuse the words on purpose, so they stick.

How to use this book

  1. Read chapters 1 through 6 once, in order. They are the spine. TinyLink, a short-link service, is built in full so you can see every step.
  2. Read chapters 7 through 18 as the catalog. Each one is a tool you pick up when a design needs it.
  3. Study the worked systems in chapter 19 by covering the page and trying the ten-line script in chapter 20 before you peek.
  4. Study the LLD half the same way: rules first, then one drill a day from chapter 28.
  5. Keep the checklists and the glossary printed beside you when you practice.
Assumptions in estimates are labeled as assumptions. Change the assumption and the arithmetic changes. The method stays.

1. The two maps

A system is a set of parts that cooperate to do a job for a user. System design is deciding those parts, the messages between them, the facts they remember, and the behavior when a part is slow or gone.

High-level design answers: which big parts exist, how a request travels, where data lives, how the system grows, and what fails first.

Low-level design answers: inside one program, which classes exist, which method calls which, what a table looks like, and how two actions at the same moment stay correct.

HLDLLD
ZoomCityOne building

A finished sentence“Open-link checks the cache, then the database, then returns a redirect.”“LinkService.open calls cache.get, then repository.findByCode.”
Done whenSomeone else can see traffic, storage, and failureA programmer can write the classes without guessing the rules

HLD chooses the buildings. LLD designs the rooms of the building you were asked to open. A design is complete only when both are filled for the parts that matter.

The cast, in one sitting

Client. The phone, browser, or other program that starts a request. It draws the screen and sends messages. It does not hold the world’s data.

Server. A computer that waits for messages and answers. An application server runs your rules. A stateless application server stores no user session in its own memory between requests. Any copy can serve any user. The database remembers. The server works and forgets. Stateless servers are easy to multiply: put a new copy behind the door and it is useful immediately.

Request and response. One message out, one message back.

API. The menu of allowed requests. Each item has a name, inputs, and the shape of the answer.

Database. The notebook that still has your facts after a restart. Memory on a server is a whiteboard. Restart wipes it.

Cache. A small, fast shelf of copies in front of a slower notebook. A hit means the copy was there. A miss means you read the notebook and usually refill the shelf.

Load balancer. The door that spreads arriving requests across many copies of a server.

Replication. Keeping extra copies of data. The leader (also called primary) accepts new writes. Followers (replicas) copy the leader. Failover is a follower becoming the leader after the leader stops.

Shard. A horizontal slice of data on its own machine. Users A–M on one notebook, N–Z on another, is sharding.

Queue. A tray of work to do soon. The user can get an answer before the slow chore finishes. Workers empty the tray.

CDN. Content delivery network. Copies of files kept in many cities, close to the user.

Latency. How long one person waits after an action. Throughput. How many actions finish per second. QPS means queries per second.

Availability. The fraction of time the system answers successfully. Three nines, 99.9%, is about 8.8 hours of silence in a year. Four nines, 99.99%, is about 53 minutes. Five nines is about 5 minutes.

Consistency. After a write succeeds, which readers see that write, and how soon. Strong consistency means a read after a successful write sees that write. Eventual consistency means readers see it after a delay, and the copies agree if new writes pause.

Authentication. Proof of identity. Authorization. Proof this identity may do this action.

Idempotent. Repeating the same request leaves the same result as doing it once.

Five questions every design answers

  1. Who talks to whom?
  2. What happens on the important action, step by step?
  3. What happens when many people do it at once?
  4. What happens when a machine dies or a network link splits?
  5. What is remembered, for how long, and who is allowed to change it?

2. The HLD method

Use these seven steps in order. The picture is step 5. Drawing boxes before you know the actions produces a poster, not a design.

  1. Requirements. Functional requirements are actions a user can name. Non-functional requirements are qualities: speed, uptime, durability, privacy, cost. Also write a short out-of-scope list so the design stays bounded.
  2. Size. Writes per second, reads per second, storage, and sometimes bandwidth. State every assumption.
  3. API. The menu, including errors.
  4. Data model. Tables or documents, keys, and the lookup the hot path uses.
  5. Boxes and paths. The path the user waits on, and the path that runs after the answer.
  6. Deep dive. The one or two hard mechanisms. For a short-link service, that mechanism is how a unique short code is born.
  7. Failure and growth. What breaks first, and which single addition removes that pressure.
Say numbers out loud as guesses. A wrong guess you can revise is useful. A silent guess is invisible.

3. TinyLink, a complete HLD

TinyLink turns a long web address into a short one, such as tiny.link/aZ3kQ9. Opening the short one jumps to the long one. This chapter is the reference design. Later chapters point back to it.

Requirements

Functional

  • Create a short link from a long address.
  • Open a short link and land on the long address.
  • Optional custom ending, such as tiny.link/priya.
  • Optional expiry.
  • A click count the owner can read later.

Non-functional

  • Open is the hot path. It should return in tens of milliseconds and stay up when creates are failing.
  • Create can take longer than open.
  • Reads outnumber writes by about 100 to 1.
  • Short codes generated by the system are not easy to walk in order if we care that strangers cannot scan neighboring links. Custom names are public on purpose.

Out of scope for version 1: accounts, editing a link, a chart dashboard, and deleting a link from every browser that already saved a jump.

Size

Assumptions: 100 million new links a month. Each link is opened about 100 times. A row is about 500 bytes. Keep data 5 years. A month is about 2.5 million seconds. Peak is about twice the average.

  • Writes: 100,000,000 / 2,500,000 ≈ 40 writes per second. Peak ≈ 80.
  • Reads: 40 × 100 ≈ 4,000 reads per second. Peak ≈ 8,000.
  • Rows in 5 years: 100,000,000 × 12 × 5 = 6 billion.
  • Disk: 6 billion × 500 bytes ≈ 3 terabytes, plus index overhead. Plan for several times that, because indexes and replicas multiply storage.

One database can hold a few terabytes. The pressure is 8,000 redirects a second, so the read path needs a cache and more than one application server. The write path is calm.

API

ActionCallInputsSuccess
CreatePOST /linkslongUrl, optional customCode, optional expiresAt, requestToken201 with code and shortUrl

Status 302 means “jump there for this request.” Browsers come back next time, so expiry and click counting still see the visit. Status 301 means “this name permanently means that address.” Browsers may remember and skip you next time. TinyLink uses 302 because expiry and counts need every open to touch the service.

Errors: 400 the address is invalid or too long. 404 unknown code. 409 custom code already taken. 410 the link existed and is expired. 429 the caller is over the rate limit.

Data

links
  id            bigint primary key
  code          varchar unique
  long_url      text
  created_at    timestamp
  expires_at    timestamp null
  click_count   bigint
  request_token varchar unique null

The hot lookup is by code, so that column has a unique index. request_token makes create safe to retry: the same token inserts once and returns the same row. The long address is small text, so it lives in the row. A photo product would put the file in object storage and store only a pointer.

City map

Browser
  -> Load balancer
    -> Stateless API servers
         -> Cache, key = code
         -> SQL database
         -> Click queue -> count workers -> database

Create path. Validate the URL. If the caller supplied a custom code, try to insert it. Otherwise take the next id, encode it, insert the row. Return the short URL. Fill the cache only after the insert commits, or leave the first open to fill it.

Open path. Read cache. On a miss, read the database and fill the cache. If missing, 404. If expired, 410. Otherwise publish a click event and return 302. The person who clicked waits through the cache or database read. The counter update happens after the jump, on a worker.

How a short code is born

Base62 uses 62 symbols: digits, lowercase letters, uppercase letters. Seven characters give 627, about 3.5 trillion names. Five years of TinyLink needs about 6 billion names, so 7 characters is enough room.

A database sequence can hand out the next id. At higher write speed, each application server reserves a block, for example “I own ids 1,000,000 through 1,999,999,” and hands those out from memory. When the block is used up, it reserves another. If a server dies mid-block, the unused ids are skipped. Holes are harmless. Duplicate ids are not.

Encoding is repeated division by 62. Remainders become characters. The same id always becomes the same code. Decoding reverses it, which tells you the shard later if you shard by id range.

Custom codes skip the encoder. The unique index on code lets one insert win. The loser gets 409.

A hash of the long URL can also make a code. Two different URLs can hash to the same characters. You then check the notebook and retry with more characters. The counter design avoids that collision on the ordinary path, so this design uses the counter. Hashing is a fair choice when you want the same long URL to keep the same short code without a lookup table of ids, and you accept collision handling.

4. Size math you can do on paper

Use powers of ten so the arithmetic fits in your head.

FactHandy figure
Seconds in a dayabout 105 (86,400)
Seconds in a monthabout 2.5 × 106
Seconds in a yearabout 3 × 107
1 million requests a dayabout 12 per second
1 million requests a monthwell under 1 per second
A characterabout 1 byte of text, more if you store rich Unicode details
A million bytes1 MB
A thousand MB1 GB
A thousand GB1 TB
A typical server network card1 to 10 gigabits per second. Divide by 8 to get bytes

QPS = total actions in the period ÷ seconds in the period. Then multiply by a peak factor, often 2× for a daily product and higher for a product that spikes at a single event.

Storage = rows × bytes per row × replicas × years. Add a factor of 2 or more for indexes and waste. Object storage for video is separate: minutes × bitrate. A 1 Mbps stream for one hour is 1 × 3600 / 8 ≈ 450 MB.

Cache memory = hot keys × value size × overhead. You rarely cache everything. Cache the working set, the slice that is read over and over. If 20% of links receive 80% of opens, size the cache for that 20% plus room to grow.

Bandwidth = QPS × bytes on the wire. Redirects are small. Video is large. A product that moves pictures will hit the network before it hits the CPU.

Write the assumption beside the result. “40 writes/s if we take 100 million creates a month.” When the real number is 10×, you know which box to revisit.

5. APIs, HTTP, and contracts

An API is a promise. Clients depend on the name, the inputs, the outputs, and the errors. Changing a promise without a plan breaks people you cannot see.

HTTP methods

MethodUsual meaningSafe to retry?
GETRead. Should not change dataYes
POSTCreate, or run an actionOnly if you add an idempotency key
PUTReplace this resource with this bodyYes, if the same body replaces the same resource
PATCHChange some fieldsDepends on the patch. “Set status to paid” is safe to retry. “Add 1 to count” is not, unless the server deduplicates
DELETERemoveYes. Deleting twice ends with the resource gone

GET, PUT, and DELETE are designed to be idempotent. POST is the one you protect with a request token (idempotency key): the server stores the token with the result and returns the original result on a replay.

Shapes of a good contract

  • Nouns in paths: /links/{code}. Verbs belong in methods, or in a clearly named action when HTTP has no natural verb.
  • Ids in the path. Filters in the query string: /messages?conversationId=9&limit=50.
  • One error body shape everywhere: a code, a human message, and a field name when a field is wrong.
  • Version the contract when a change would break old clients. A path prefix /v2 is the blunt tool. Adding optional fields is usually safe. Removing or renaming fields is a break.
  • Paginate lists. Offset pagination (page=5&limit=20) is easy and gets slow and skippy when rows are inserted at the top. Cursor pagination returns “give me 20 items older than this id.” It stays fast because it uses the index, and it stays stable while new rows arrive.

Timeouts, from the caller’s side

Every call to another machine has a deadline. A client that waits forever holds a worker on your server, which holds a worker on the next server. Pick a budget for the whole user request, then give each hop a smaller budget. If the hop misses the budget, fail that hop and follow your retry rule.

6. Data that survives a restart

Choose storage from the questions you ask, not from fashion.

SQL databases

Data sits in tables of rows and columns. A primary key identifies one row. A foreign key is a column that points at a primary key in another table, such as likes.photo_id pointing at photos.id. The database can refuse a like that points at a missing photo.

SQL is a strong fit when facts must match, when you join them in different combinations, and when a bundle of writes must all stick or all roll back. Users, orders, money, seats, and short links belong here.

Normalization means each fact lives in one place.

  • First normal form: each column holds one value, not a secret list stuffed into a text field. “tags = cat,dog” makes “find every photo tagged cat” a scan.
  • Second: every non-key column depends on the whole key, not on a piece of it.
  • Third: a non-key column depends on the key, not on another non-key column. A user’s city belongs on the user row. Copying the city onto every photo means a move requires updating every photo.

Sometimes you copy a fact on purpose. That copy is denormalization. You do it when a join on the hot path is too expensive, and you accept the job of keeping the copy honest.

Indexes

An index is an extra structure that answers a lookup without reading every row. The usual structure is a B-tree: ordered, good for equality and for ranges such as “photos newer than Tuesday.” A hash index answers equality and does not help ranges.

A composite index on (user_id, created_at) serves “this user’s newest photos.” It also serves “this user” alone, because user_id is the leftmost column. It does not serve “all photos from Tuesday” by itself, because created_at is not the leftmost column. This is the leftmost prefix rule.

A covering index contains every column the query needs, so the database can answer from the index alone.

Indexes speed reads and cost writes, because every insert and update maintains them. Index the lookups you actually run. A table with ten unused indexes pays for those ten on every write.

NoSQL, in three useful shapes

Key-value. One key, one blob. Session data, cache, shopping cart, “feed for user 42.” Extremely fast when the access is always by that key.

Document. A key and a JSON-like document you can query inside. A good fit when one aggregate, such as a product with its variants, is always loaded together, and different products have slightly different fields.

Wide-column. A row key and many columns, spread across machines. A fit for huge write streams such as time-series events and messages keyed by conversation.

These systems often push joins and multi-row transactions up into your code. You pick them when the key-based access and the scale are the point.

Object storage

Photos, video, and backups go in object storage: a giant closet of blobs addressed by a key. The database stores the key, the owner, and the time. You do not put a 4 MB photo inside every SQL row. Object storage is cheap per byte and slow compared with a cache of small metadata. Put a CDN in front when many users download the same blob.

Choosing

You mostly…Lean toward
Join orders, users, and payments, and need transactionsSQL

The source of truth is the store whose answer wins when copies disagree. Caches, search indexes, and feed timelines are derived. They can be rebuilt from the source of truth.
